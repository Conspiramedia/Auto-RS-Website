# Автоматическое тестирование

Живых тестировщиков у проекта нет: единственный рубеж между ошибкой и
продом — прогон на каждый пуш. Этот документ описывает, что проверяется,
как запустить локально и как добавить новый тест.

---

## 1. Окружение: почему локальный Supabase

Тесты **никогда не касаются боевой базы**. Выбран локальный стек
Supabase в Docker, а не второй облачный проект.

**Почему так:**

- **Детерминированность.** `supabase db reset` заново накатывает
  миграции и seed, поэтому каждый прогон начинается с известного
  состояния. Общая облачная база такого не даёт: два прогона подряд
  влияли бы друг на друга, а параллельные ветки в CI дрались бы за одни
  и те же строки.
- **Никаких секретов в CI.** Ключи локального стека фиксированы и
  одинаковы у всех — они лежат в `.env.test` прямо в репозитории. Для
  облачного проекта пришлось бы заводить секреты GitHub и следить, чтобы
  в них не попал боевой ключ.
- **Схема не расходится.** Локальный стек накатывает те же миграции из
  `supabase/migrations`, что уезжают на прод. Отдельный облачный проект
  надо поддерживать вручную, и он неизбежно отстаёт.

### Два рубежа защиты от прогона по проду

`.env.local` в этом проекте указывает на **боевой** Supabase — так
устроена разработка. Поэтому защита двойная:

1. **`.env.test`** перекрывает адреса. Все npm-скрипты тестов идут через
   `dotenv -e .env.test`, поэтому боевые значения не подхватываются.
2. **`tests/env.ts`** проверяет адреса ещё раз, до запуска первого
   теста, и падает с объяснением, если они указывают на `rsauto.rs` или
   облачный `supabase.co`. Работает, даже если `.env.test` потеряется.

Тот же рубеж стоит в SQL-тестах: `supabase/checks/0085_auth_gates_test.sql`
отказывается работать, если не находит тестового админа из seed, а
`scripts/run-sql-checks.mjs` проверяет, что адрес базы — localhost.

### Если Docker не запущен

Docker на машине разработчика есть, но не всегда поднят. Прогон это
переживает:

| Проверка | Без Docker |
|---|---|
| `tsc`, `build` | работают |
| Публичные страницы, SEO, i18n, a11y | работают на страницах без данных |
| Карточка объявления, каталог с данными | **пропускаются** (`test.skip` с внятной причиной) |
| SQL-тесты гейтов | **пропускаются**, прогон остаётся зелёным |

Пропуск не красит CI в красный: в GitHub Actions Docker есть всегда, и
там стек поднимается заранее, поэтому пропуск возможен только локально.

Из последнего полного прогона: **382 теста прошли, 28 пропущены**
(десктоп + мобильный), падений нет. Пропущены ровно те, что зависят от
данных: каталоги, карточка объявления и её JSON-LD, `ItemList`,
подписи фотографий.

### Две ловушки, на которые уже наступали

Обе стоили времени при отладке — если тест падает необъяснимо, начните
с них.

**1. Порт 3000 занят `next dev`.** Playwright с `reuseExistingServer`
молча подхватывал чужой дев-сервер вместо своей сборки: прогон
«работал», но проверял dev-версию — с HMR-сокетом, сыплющим 403 в
консоль, и без статической генерации, на которой держатся все
SEO-проверки. Поэтому тесты живут на **3100**. Если порт занят
процессом от прошлого прогона, освободите его — иначе Playwright
переиспользует сервер со старой сборкой, и вы увидите ошибки вида
«Refused to execute script … MIME type text/plain».

**2. CSP и локальный Supabase.** `connect-src` в `next.config.mjs`
собирается из `NEXT_PUBLIC_SUPABASE_URL`. Раньше origin склеивался как
`https://` + хост, из-за чего локальный `http://127.0.0.1:54321`
превращался в `https://127.0.0.1` — без порта и с чужим протоколом.
Браузер блокировал **каждый** запрос к базе («Refused to connect»), и
локально не работали ни вход, ни подача объявления. Исправлено:
origin берётся целиком через `new URL(...).origin`. Симптом, если
что-то похожее вернётся, — `TypeError: Failed to fetch` в интерфейсе и
сообщение про Content Security Policy в консоли.

## 2. Запуск локально

### Полный прогон (нужен Docker)

```bash
npm run supabase:start
```

```bash
npm run supabase:reset
```

```bash
npm run test:e2e
```

`supabase:reset` накатывает все миграции и заливает `supabase/seed.sql`.
`test:e2e` сам соберёт сайт и поднимет сервер на `127.0.0.1:3100`.

> **Порт 3100, а не 3000 — намеренно.** На 3000 обычно работает
> `next dev`, и Playwright молча подхватывал бы его вместо своей
> сборки: прогон «работал» бы, но проверял дев-версию — с HMR-сокетом,
> сыплющим ошибки в консоль, и без статической генерации, на которой
> держатся все SEO-проверки. Отдельный порт снимает и обратную
> неприятность: тесты не займут порт, на котором вы работаете.

### Быстрый прогон без Docker

```bash
npm run test:e2e
```

Тесты, которым нужны данные, пропустятся с объяснением. Остальное —
SEO-разметка, доступность, локализация, служебные файлы — проверяется
полностью.

### Отдельные сьюты

```bash
npm run test:seo
```

```bash
npm run test:a11y
```

### Разбор падений

```bash
npm run test:report
```

Открывает HTML-отчёт с трейсами. Трейс — это запись прогона с
DOM-снимками на каждом шаге; без него разбирать упавший в CI тест
практически невозможно.

Режим с интерфейсом, где можно шагать по тесту:

```bash
npm run test:e2e:ui
```

### SQL-тесты серверных гейтов

```bash
npm run test:sql
```

Требуют поднятого Supabase и `psql` в `PATH` (входит в клиент
PostgreSQL; Supabase CLI его не ставит).

### Lighthouse

```bash
npm run lhci
```

### SQL, на настоящей базе

`supabase/checks/0085_auth_gates_test.sql` — семь тестов гейта входа по
почте: админа пропускает; не-админу и несуществующему адресу отказывает;

проверка админства не выдана анониму.

Транзакция откатывается — тест не оставляет следов.

## 4. Что остаётся ручным

Автоматизировать это нельзя или нецелесообразно:

- **Сквозной вход по настоящему коду.** UI-тесты перехватывают запросы к
  Supabase и до отправки SMS/письма не доходят. Проверка «код пришёл →
  введён → сессия создана» требует живого номера и провайдера SMS.
- **Валидаторы поисковиков.** Rich Results Test, Facebook Sharing
  Debugger, Twitter Card Validator забирают страницу по публичному URL —
  локальный сервер им недоступен. Запускаются после деплоя (пункты в
  `RELEASE.md`).
- **Визуальная оценка.** Тесты видят разметку, а не то, «красиво ли».
  Вёрстка на трёх брейкпоинтах проверяется глазами.
- **Реальные письма.** Доставляемость, вид письма в почтовом клиенте,
  попадание в спам.
- **Модерация с телефона.** Админка проверяется тестами на уровне
  доступа; удобство работы с неё — вручную.

## 5. Как обновлять seed

Данные живут в **двух местах, и они обязаны совпадать**:

- `supabase/seed.sql` — сами строки в базе;
- `tests/fixtures/seed.ts` — те же идентификаторы и значения для тестов.

Разойдись они — тест упадёт с «страница 404» или «цена не совпала», и
причина будет неочевидна.

**Порядок правки:**

1. Измените `supabase/seed.sql`.
2. Отразите изменение в `tests/fixtures/seed.ts` — идентификаторы, цены,
   статусы.
3. Пересоберите базу и прогоните тесты:

```bash
npm run supabase:reset
```

```bash
npm run test:e2e
```

**Что уже есть в seed:** админ (вход по почте), продавец (вход по
телефону), салон; пять объявлений — продажа `active`, аренда `active`,
и продажа и аренда сразу, `moderation`, `archived`. Такой набор
покрывает все ветки отображения карточки и проверку того, что скрытые
объявления не утекают в каталог и карту сайта.

В конце `seed.sql` стоит блок контроля: если строк меньше ожидаемого,
`supabase db reset` падает сразу с понятным сообщением, а не оставляет
тесты падать дальше по цепочке.

## 6. Как добавить тест

### Новая страница

Добавьте её в `tests/fixtures/pages.ts` → `PUBLIC_PAGES`. Она сразу
попадёт в проверки доступности, SEO-тегов, canonical, hreflang и
локализации — отдельного теста писать не нужно.

```ts
{ path: '/новый-раздел', name: 'Новый раздел', indexable: true, needsData: false }
```

Если страница тяжёлая и её стоит проверять axe и Lighthouse — добавьте
её в `KEY_PAGES` там же.

### Новый сценарий

Файл `tests/e2e/<имя>.spec.ts`. Правила проекта:

- **Селекторы по ролям и доступным именам**, а не по классам:
  `getByRole('tab', { name: 'E-mail' })`. Классы Tailwind меняются при
  каждой правке вёрстки, роли — нет. Побочная польза: тест заодно
  проверяет доступность.
- **Сообщение в `expect` объясняет поломку**, а не повторяет условие.
  Не «ожидалось true», а «на /contact нет Organization».
- **Данные — из фикстур**, не из литералов в тесте.
- **Нет данных — `test.skip` с причиной**, не падение: отсутствие
  Docker не должно выглядеть как поломка кода.

### Новая серверная проверка

Файл `supabase/checks/<номер>_<имя>_test.sql`. Суффикс `_test.sql`
обязателен: `scripts/run-sql-checks.mjs` берёт только их. Рядом лежат
файлы `_verify.sql` — они только читают каталоги и предназначены для
ручного просмотра.

Шаблон: `begin` → защита от боевой базы → блоки `do $$ … raise exception`
→ `rollback`.

**Правило границы.** В SQL проверяются *правила* (кого пускать, сколько
раз), в Playwright — *поведение интерфейса* (что показано, что
заблокировано). Мок, повторяющий логику гейта, проверял бы сам себя.

## 7. CI

`.github/workflows/ci.yml`, на push и pull request в `main`:

| Работа | Что делает |
|---|---|
| **build** | `tsc` и `next build`, сборка сохраняется артефактом для остальных работ |
| **e2e** | Playwright на двух проектах (desktop и mobile) параллельно, с поднятым Supabase |
| **sql** | SQL-тесты гейтов |
| **lighthouse** | Бюджеты качества |

Порядок от дешёвого к дорогому: типы и сборка падают за минуту и
отменяют смысл гонять получасовой Playwright.

**Артефакты при падении:** HTML-отчёт, трейсы, скриншоты и видео —
вкладка Actions → прогон → Artifacts, хранятся 7 дней.

Новый пуш в ту же ветку отменяет предыдущий прогон (`concurrency`).
