# RS Auto — сайт маркетплейса автомобилей (Сербия)

Next.js 16 (App Router, TypeScript, Tailwind) + Supabase.

Сайт — **второй клиент того же Supabase**, что и мобильное приложение
(`D:\Project\Auto.RS`). Собственной базы у сайта нет, сущности не дублируются:
вся бизнес-логика живёт в PostgreSQL (RPC, триггеры, RLS), фронтенд только
вызывает функции и отображает результат.

---

## Запуск

```bash
npm install
```

Скопируйте `.env.example` в `.env.local` и заполните значения:

```bash
cp .env.example .env.local
```

| Переменная | Назначение |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | URL проекта Supabase (тот же, что у приложения) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Публичный anon-ключ |
| `NEXT_PUBLIC_SITE_BASE_URL` | Базовый адрес сайта для canonical, OG и sitemap |

`SERVICE_ROLE` сайту **не нужен и не должен добавляться**: весь публичный
контент доступен анониму через RLS и `SECURITY DEFINER` RPC.

Разработка и сборка:

```bash
npm run dev
```

```bash
npm run build
```

```bash
npm run typecheck
```

## Миграции Supabase

**Единый источник истины схемы — этот репозиторий:**
`supabase/migrations/`. В репозитории приложения (`D:\Project\Auto.RS`)
миграций нет — там остался только `supabase/README.md` с указателем
сюда. Два счётчика в двух репозиториях дали бы два файла с одним
номером.

Нумерация сплошная, миграции **аддитивные**: сигнатуры RPC, которые
вызывает приложение (`search_cars_advanced`, `approve_car`,
`reject_car` и остальные), не менялись ни разу.

Применить:

```bash
supabase db push
```

Связь CLI (`supabase link`) настроена здесь же. Проверка перед
применением:

```bash
supabase db push --dry-run
```

Проверочные скрипты к миграциям — `supabase/checks/`. Файлы
`*_verify.sql` ничего не меняют: читают системные каталоги и печатают
«ok» или то, что пошло не так; запускаются в SQL Editor **после**
применения соответствующей миграции.

Файлы `*_test.sql` — поведенческие тесты серверных гейтов. Они создают
временных пользователей и объявления, поэтому идут **только против
локального стека** и в конце откатывают транзакцию:

```bash
npm run supabase:start
npm run supabase:reset   # применит миграции и seed
npm run test:sql
```

Запускать их на боевой базе нельзя — раннер это и проверяет, отказываясь
работать с не-localhost. Без Docker тесты пропускаются с предупреждением,
а не падают.

Заметные миграции последнего времени:

| Файл | Содержимое |
|---|---|
| `0071_email_queue.sql` | Очередь писем, триггеры уведомлений, `profiles.locale` |
| `0077_car_site_url_locale.sql` | Канонический адрес объявления с учётом локали получателя |
| `0078_admin_room.sql` | Админка: журнал `admin_action_log`, `admin_guard`, сводка, журналирование в `approve_car`/`reject_car` |
| `0079_admin_queue.sql` | Очередь модерации и карточка объявления для проверки |
| `0080_admin_listings_users_log.sql` | Все объявления, пользователи, журнал; письмо о снятии объявления |
| `0089_status_matrix_authority.sql` | Авторство снятия (`cars.archived_by`): владелец не возвращает объявление, снятое администратором. Плюс единый триггер гашения продвижения, журнал по каждому объявлению при блокировке салона и запрет автопубликации для ранее отклонённых |

**`0054_seed_site_demo.sql` на боевую базу не применять** — демо-объявления
попадут в каталог и sitemap. Удаление — [`docs/cleanup_demo.sql`](docs/cleanup_demo.sql).

### Справочники фильтров

Два разных источника, и это осознанно:

- **Фильтры** (`lib/referenceData.ts` + RPC `get_car_models`) — **полный
  справочник**, как в приложении: 117 марок, 18 городов онбординга, все
  модели марки. Пользователь, пришедший из приложения, видит привычный
  список. Выбор марки без объявлений даёт empty state с подпиской
  «Сообщить, когда появится», а не пустой экран.
- **SEO-страницы и sitemap** (`get_site_brands/models/cities`) —
  **только живые данные**. Страница для марки без объявлений не
  создаётся: `/cars/ferrari` отдаёт 404. Массово проиндексированные
  пустые страницы (thin content) вредят сайту.

Списки enum'ов (кузов, коробка, топливо) обязаны совпадать со значениями
в БД — они уходят в фильтр как есть и сравниваются с типом PostgreSQL.

**Все справочные поля выбираются из списка** (`components/ListPicker.tsx`),
как в приложении: свободного текста нет ни в фильтрах, ни в форме подачи.
Компонент повторяет пикер приложения — поиск по списку, пункт «Все»,
галочка у выбранного. На мобильных открывается шитом снизу, на десктопе —
дропдауном под полем. Значение уходит в URL через скрытый `input`, поэтому
фильтры работают на обычной GET-форме и страница остаётся SSR.

Поиск нормализует диакритику и регистр, поэтому «uzice» находит «Užice» —
на сайте это важнее, чем в приложении: сербской раскладки у пользователя
может не быть.

В **форме подачи** марка/модель/город дополнительно позволяют ввести своё
значение через «Указать «…»» — это `allowCustom: true` приложения.
Продавец с редкой маркой или из небольшого города должен иметь возможность
подать объявление; справочник `car_brands` пополняется триггером.

### Локализация

- `sr` (латиница) — язык по умолчанию, живёт в корне сайта без префикса;
- `ru` — префикс `/ru/`;
- отдельной кириллической версии сербского **нет**: двуалфавитность решается
  нормализацией поиска на бэкенде (`f_normalize`), а не дублями страниц;
- `canonical` всегда указывает на сербскую версию, версии связаны `hreflang`.

### Дизайн-токены

Цвета, радиусы, сетка отступов и шрифт — в `lib/brand.ts`, перенесены из
приложения (`lib/core/theme/app_theme.dart`, `app_button_colors.dart`).
Tailwind берёт значения оттуда же. **Правка бренда делается только в этом файле.**

## Что уже работает

- **Карточка `/car/{id}`** — SSR, canonical, hreflang, OG + динамическая
  OG-картинка, JSON-LD (`Vehicle` + `Offer`), галерея, «Продолжить в
  приложении», QR на десктопе, «Поделиться», похожие объявления.
  Проданные (`sold`) открываются по прямой ссылке с плашкой и
  `availability: SoldOut`.
- **Каталог `/cars`** — фильтры в URL (SSR), чипсы применённых фильтров с «×»,
  сортировка ссылками, пагинация, empty state с причиной, сбросом и
  «Сообщить, когда появится». Mobile-first.
- **Аренда `/rent`** — отдельная витрина со своими SEO-страницами
  `/rent/{brand}` и `/rent/{brand}/{model}`, переключатель «Продажа | Аренда»
  в шапке каталога. Цена показывается за сутки, фильтр цены и сортировка
  работают по суточной ставке. Карточка аренды показывает залог и блок
  условий; объявление может быть одновременно на продажу и в аренду —
  тогда видны обе цены и два `Offer` в JSON-LD.
- **SEO-страницы** `/cars/{brand}` и `/cars/{brand}/{model}` — SSG по маркам
  и моделям, у которых есть активные объявления, хлебные крошки JSON-LD,
  перелинковка на модели.
- **Подача `/sell`** — 4 шага, вход по SMS (`rpc_check_otp_quota` →
  `signInWithOtp` → `verifyOtp`), загрузка фото в `car-images/{uid}/`,
  `create_car_v2`. Объявление создаётся со статусом `moderation`.
- **Антиспам** — honeypot в обеих формах, суточная квота OTP (5/номер),
  лимит заявок дилеров (3/номер) на стороне БД.
- **`sitemap.xml`** с hreflang-альтернативами, **`robots.txt`**,
  **`.well-known/`** для deep links.

### Админ-комната `/admin`

Модерация переехала на сайт: раздел `/admin` — рабочий инструмент для
двух-трёх человек, только на русском, без зеркала `/ru/admin`.

Разделы: дашборд со сводкой, очередь модерации, все объявления,
пользователи, журнал действий. Миграции `0078`–`0080`.

Вторая система прав при этом не заводится: используется та же роль,
что и в приложении — `profiles.is_admin`, тот же хелпер `is_admin()`,
те же RPC `approve_car` / `reject_car`. Флаг админа ставится вручную
в SQL Editor, через интерфейс не редактируется.

Защита — три слоя, и решающий из них последний:

1. `proxy.ts` — только локаль: `/admin*` исключён из редиректа на
   префикс языка. Ролями proxy не занимается (документация Next прямо
   запрещает использовать его как авторизацию).
2. `app/admin/layout.tsx` — серверная проверка `admin_guard()`; при
   `false` — `notFound()`. Именно 404, а не 403: гость и не-админ
   неразличимы, существование раздела не подтверждается. Метаданные —
   `noindex, nofollow`.
3. **Истинная защита** — `is_admin()` первой строкой в каждой админской
   RPC. Слои 1–2 всего лишь не рисуют интерфейс тому, кто всё равно
   ничего не сможет сделать.

Журнал `admin_action_log` (миграция `0078`) — append-only: RLS deny-all
плюс явный `revoke` табличных грантов (RLS не отменяет гранты, нужны оба
замка), `UPDATE`/`DELETE` не выдаются никому. Пишет в него только
`f_admin_log()`, и автор берётся из `auth.uid()` внутри функции, а не из
параметра — иначе журнал ничего не доказывал бы. Запись идёт в одной
транзакции с решением модерации: одобрение без записи в журнал
невозможно.

Экран модерации в приложении остаётся рабочим и не развивается —
Flutter-версии админки не будет (см. `CLAUDE.md`, п. 1).

#### Как войти администратором

Отдельного «входа для админов» нет и не будет: это обычный аккаунт
сайта, которому в базе поднят флаг. Порядок — один раз на человека:

1. **Войти на сайт как обычный пользователь** — `/login`, вход по
   SMS на **сербский мобильный номер** (`+381 6X XXX XXX`).
   Это создаёт запись в `auth.users` и профиль в `profiles`.

   Второй способ — **вход по почте** (вкладка «Почта» на `/login`):
   код из письма вместо SMS. Он доступен **только администраторам** —
   гейт `email_login_allowed` (миграция `0082`) — и открывает
   существующий аккаунт, а не создаёт новый. Заведён потому, что
   первый администратор площадки зарегистрирован без телефона.
   Подключение хука отправки — `RELEASE.md`, пункт 6b.

2. **Поднять флаг вручную в Supabase SQL Editor.** Через интерфейс
   это не делается ни при каких условиях — скомпрометированный
   аккаунт администратора не должен уметь плодить администраторов:

   ```sql
   -- Сначала убедиться, что профиль существует и это нужный человек.
   select id, email, phone, full_name, is_admin
     from public.profiles
    where phone = '+3816XXXXXXXX';   -- или where email = '...'

   -- Затем поднять флаг ровно этому id.
   update public.profiles set is_admin = true
    where id = 'UUID-ИЗ-ПРЕДЫДУЩЕГО-ЗАПРОСА';
   ```

   Обновлять по `id`, а не по телефону или почте: адрес меняется, а
   промах в `where` при `update` затрагивает не ту строку молча.

3. **Открыть `/admin`.** Флаг читается на каждом запросе
   (`admin_guard()` → `is_admin()` → `profiles.is_admin`), поэтому
   перезаходить не нужно — достаточно обновить страницу.

**Снять права** — тем же запросом с `is_admin = false`. Действует
немедленно: роль спрашивается у базы, а не берётся из токена, поэтому
уволенный модератор не сохраняет доступ до истечения сессии.

**Если `/admin` отдаёт 404** — это штатный ответ для всех, кто не
администратор, включая гостей: 403 подтверждал бы существование
раздела. Проверять в таком порядке: есть ли сессия (`/my` открывается
без формы входа), поднят ли флаг (`select is_admin from profiles where
id = auth.uid()` под сессией этого пользователя).

Ссылку `?redirect=/admin` страница входа обрабатывает корректно:
`/admin` не получает префикс локали, и модератор с русской cookie
попадает на `/admin`, а не на несуществующий `/ru/admin`
(`localeAwareHref` в `lib/i18n.ts`).

#### Что администратор может и чего не может

| Может | Не может |
|---|---|
| Одобрять и отклонять объявления (причина обязательна, ≥10 символов) | Выдавать и снимать права администратора |
| Снимать с публикации и возвращать (причина обязательна) | Редактировать чужие объявления |
| Видеть почту, телефон и статистику пользователей | Удалять записи журнала — `UPDATE`/`DELETE` не выданы никому |
| Читать журнал всех действий, включая свои | Изменить автора записи в журнале: он берётся из `auth.uid()` |

Каждое решение пишется в `admin_action_log` в той же транзакции, что
и само изменение, — одобрение без записи в журнал невозможно.

### Замечания

- Бронирование аренды на сайте не реализовано: даты, расчёт стоимости и
  оплата живут в приложении (`bookings`, `pay_booking`). Сайт показывает
  условия и ведёт в приложение — как и в случае с чатом.
- Минимальный срок аренды на карточке зафиксирован как «1 сутки»: в схеме
  это глобальная константа приложения (`AppConstants.minRentDays`), поля
  на уровне объявления нет. Если продавцам понадобится свой минимум —
  потребуется колонка в `cars` и правка `create_car_v3`.
- Строки на сербском не вычитаны носителем языка.
- **Поиск кириллицей по латинским названиям не работает** — запрос «БМВ»
  не находит «BMW». Причина в исходной схеме: `f_normalize` — это
  `unaccent + lower`, а `unaccent` снимает диакритику (Đ Č Š Ž), но не
  транслитерирует кириллицу в латиницу. Поведение одинаково на сайте и
  в приложении (`search_cars_advanced`), регрессии нет. Латиница и поиск
  по городам работают. Решение — таблица транслитерации или расширение
  `f_normalize`; затрагивает и приложение, поэтому требует отдельной задачи.

## Деплой (Vercel)

Боевой адрес: **https://rsauto.rs**

Автодеплой при пушах **отключён** (`vercel.json` → `git.deploymentEnabled: false`).
Публикация выполняется вручную:

```bash
vercel --prod
```

Переменные окружения задаются в Vercel (Settings → Environment Variables),
scope Production и Preview:

| Переменная | Значение |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | URL проекта Supabase |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Публичный anon-ключ |
| `NEXT_PUBLIC_SITE_BASE_URL` | `https://rsauto.rs` |

Ключи из блока «только для скриптов» (`SUPABASE_SERVICE_ROLE_KEY`,
`UNSPLASH_ACCESS_KEY`, `PEXELS_API_KEY`) на Vercel **не задаются**: они нужны
только разовым локальным скриптам, а сервисный ключ работает в обход RLS и
в окружении сайта присутствовать не должен.

`.well-known` отдаётся статикой из `public/`; заголовок
`Content-Type: application/json` для AASA задан в `next.config.mjs` — без него
Next отдал бы файл без расширения как `text/plain`, и iOS не засчитал бы
проверку связи домена с приложением.
